NatScript is the proposed high-level language for nat-os applications. It does not exist yet as a compiler or runtime — what's shipped today is the bytecode VM (NatVM) and a host-side assembler (vasm) that programs are written in by hand.

What exists today vs. what's planned
Layer	Status	What it is
NatVM
Shipped
Kernel bytecode interpreter — 35 opcodes, 16 registers, bounds-checked arena memory
vasm
Shipped
Assembler in tools/vasm.py; source files are *.vasm
NatScript
Conceptual
High-level language that would compile to that bytecode
Programs like paint, pong, and rogue are written in vasm assembly, not NatScript. Example from demo.vasm:

        ...

You write register operations and sys calls; vasm assembles them into a C header (kernel/generated/*.h) that the kernel loads into an app arena.

What NatScript is meant to be
The vision (from docs/conceptual/natscript-and-natvm.md and the original PDF proposal) is a language where you program a physical device at the level of intent, not registers:

NatScript source  →  compiler  →  NatOS bytecode  →  NatVM  →  device model  →  hardware
Instead of:

ldi r0, 12
ldi r1, 0
sys device    ; r0=op, r1..r4=args
You'd write something closer to:

device scanner;
when button.pressed {
    display.show(result);
}
every 10ms {
    balance.update();
}
The goal stated in the docs:

Make physical computing feel like programming a computer, rather than programming a collection of electrical components.

The real product isn't the syntax
The revised proposal is explicit: isolation is the product; NatScript is how you reach it.

MicroPython, CircuitPython, Arduino, and Espruino all win on ecosystem and familiarity. What they don't offer on a microcontroller is application isolation — one crashing program takes everything down.

nat-os already has:

Per-app arenas with bounds-checked loads/stores
Viewport confinement (can't draw outside your strip)
Device permissions (UM-NATOS-032)
Fault isolation (one app dies, neighbors keep running — verified by programs like gfxrogue that try to escape)
NatScript would sit on top of that stack, not replace it.

Planned language features
From the proposal, the distinctive syntax ideas are:

device declarations — nearly free now. The kernel already has a device table reached via sys device; a NatScript device scanner; would be a compile-time lookup against that table.

when / every — event-driven and periodic code. These look like two syntaxes but are one VM feature: the kernel must be able to call into a program at a handler, not just resume its main loop.

permissions { ... } — declare which devices an app may use. The enforcement hook already exists (device_read(caller, ...)); what's missing is strong image identity/signing before calling it "security."

What's blocking a real NatScript compiler
Several VM gaps must be closed first (documented in docs/next_moves/02-vm-events-and-frames.md):

Stack frame convention — call/ret exist, but the 16 registers are global. A compiler needs a decided convention for locals and nested calls (likely arena-backed frames).

Multiple entry points — partially done. sys event and VM_EVT_TICK / VM_EVT_KEY exist; app_evt.vasm is the first program the kernel calls into:

spin:
        add     r10, r10, r11       ; main loop does nothing; handlers do the work
        jmp     spin
Documented syscall ABI — register-positional (sys fill wants r0–r4 in specific roles); fine for hand assembly, needs formal spec before a compiler depends on it.

No floating point — fixed-point only, as the raycaster already does.

Honest sequencing (if NatScript ever ships)
From the revised proposal:

Document the bytecode ABI properly
Fix the frame convention in the VM
Finish event delivery (when / every prerequisites)
Add permissions checks against the manifest
Then build a minimal NatScript compiler
Rewrite app_dev.vasm in NatScript — if it's not shorter and clearer than assembly, the language hasn't earned itself
Phases 1–3 are VM work with no language in sight.

Bottom line
NatScript = the planned high-level language for nat-os apps, oriented around devices, events, and permissions.

Today = you program in vasm (assembly targeting NatVM), which is mature enough for real apps (paint, launcher, 3D demo, note pad).

Why it matters = not to compete with Python on syntax, but to give isolated, permissioned apps a readable interface to hardware nat-os already controls safely.

If you want to go deeper, the best reads are docs/conceptual/natscript-and-natvm.md (revised proposal), docs/book/14-the-isa.md (what the VM actually implements), and tools/app_evt.vasm (closest thing to what when/every would compile to).

Example code:

app Scanner {

    permissions {
        use scanner
        use display
        use buttons
    }

    device scanner: BarcodeScanner
    device display: Screen
    device buttons: Buttons

    state {
        last_code: String
        scan_count: Int
    }

    start {
        display.clear()
        display.text("Ready")
    }

    when buttons.scan_pressed {
        let code = scanner.scan()

        if code.is_valid {
            state.last_code = code
            state.scan_count += 1
            display.text(code)
        }
    }

    every 1s {
        display.status("Scans: " + state.scan_count)
    }
}
